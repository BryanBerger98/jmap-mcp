# Sieve and vacation tools

The three manifests on this page sit on two capabilities: `urn:ietf:params:jmap:sieve` for `sieve_scripts` and `sieve_write`, and `urn:ietf:params:jmap:vacationresponse` for `vacation_manage`.
A server that does not advertise one of them drops the tools of that manifest, and the startup line counts it under `domains skipped`.
Stalwart grants the two capabilities through two separate permissions, so an account may hold the vacation response without the scripts, or the scripts without the vacation response.

One script filters incoming mail at a time, and the vacation response is a script named `vacation`: activating a filter switches the automatic reply off, and switching the reply on stops whatever script was filtering.
The text of a script travels through the conversation, unlike the bytes of a file, because it is prose the user writes, reads back and corrects.

## Reading scripts

Manifest `sieve`, on the `sieve` capability alone.

### sieve_scripts

Reads the Sieve filters of the account.
`list` gives one line per script with its name, its id and whether it is the active one, and says which script is currently filtering incoming mail, or that none is.
`show` returns the full source of one script.
A script named `vacation` is generated by the vacation response and is read and changed through `vacation_manage`, never through this tool.

Class: `read`.

| Argument | Type | Required | Meaning |
| --- | --- | --- | --- |
| `action` | enum: list, show | yes | List the scripts of the account, or read the text of one |
| `nameContains` | string | no | On `list`, keep only the scripts whose name contains this; ignored on `show` |
| `id` | string | no | On `show`, the id of the script to read, as `list` returns it; required on `show` |

The schema itself refuses a `show` without `id`.

**Refuses or asks.**
An id the account does not hold is refused: `Refused: no Sieve script has the id <id>. Run sieve_scripts with action list to see what the account holds.`
A script the server holds without a source is refused: `Refused: <name> (<id>) carries no blobId, so the server has no source to hand back for it.`
A read never asks a confirmation.

There is no cursor: the listing is sorted by name, ascending, and fetches up to 100 scripts in one page, which covers the handful an account holds.
The source shown by `show` is cut at 12000 characters, and the answer then ends with `[cut here: N more bytes of this script are not shown]`.
Under a name filter, the listing never claims that nothing filters, since the active script may simply not match.

Example prompts:

> List my Sieve scripts and tell me which one is filtering my mail right now.

> Show me the source of the script called newsletters.

## Writing scripts

Manifest `sieve-writing`, on the `sieve` capability alone.

### sieve_write

Writes the Sieve filters of the account.
`store` creates a script or replaces the text of one and activates nothing: the text is compiled first, and a script that does not compile is refused with the compiler's own message.
`activate` makes one script the one that filters incoming mail, which always stops whatever was filtering before; `deactivate` leaves the account with no filtering at all; `delete` destroys scripts for good, since Sieve has no trash.
The script named `vacation` belongs to the vacation response and is written through `vacation_manage`, never here, although `deactivate` does reach it by switching off whatever script is active.

Class: `draft` on `store`, `destroy` when `action` is `activate`, `deactivate` or `delete`.

| Argument | Type | Required | Meaning |
| --- | --- | --- | --- |
| `action` | enum: store, activate, deactivate, delete | yes | Store a script without running it, make one active, switch filtering off, or destroy scripts |
| `name` | string | no | The script name; required on `store`, including a correction; `vacation` is reserved |
| `script` | string | no | The Sieve source as text; required on `store`, compiled before anything is stored |
| `id` | string | no | One script as `sieve_scripts` returns it; required on `activate`; on `store`, the script to correct |
| `ids` | string[] | no | The scripts to destroy, as `sieve_scripts` returned them; required on `delete` |

The schema itself refuses a `store` without `name` or `script`, an `activate` without `id`, and a `delete` without `ids`.
A `store` without `id` creates a new script; with `id`, it replaces the text of that script and renames it to `name`.

**Refuses or asks.**
A `store` under the reserved name is refused before any upload: ``Refused: `vacation` is the name the vacation response owns, and a script stored under it would be overwritten the next time that response is set. Use vacation_manage to change the automatic reply, or store this script under another name.``
A `store` or `activate` on an id the account does not hold is refused: `Refused: no Sieve script has the id <id>. Run sieve_scripts with action list to see what the account holds.`
A `store`, an `activate` or a `delete` aimed at the script the vacation response generates is refused on the client, because the server would carry the destruction out without a word.
An `activate` whose source cannot be read is refused rather than confirmed blind: `Refused: the source of <name> (<id>) could not be read, so this call cannot say what activating it would do to incoming mail. Nothing was activated; try sieve_scripts with action show to see whether the text is reachable at all.`
A `deactivate` when nothing is active is refused: `Refused: no script is active, so nothing filters incoming mail and there is nothing to switch off. Nothing was changed.`
A `delete` with no id, or with more than 50 ids, is refused before anything is read; see [limits](../limits.md).
A `delete` naming an unknown id, or the script currently filtering, is refused with nothing destroyed: `Refused: <name> (<id>) is the script currently filtering incoming mail, and this server never removes the active script out from under the account. Nothing was destroyed. Switch filtering off with action deactivate, or activate another script first.`
A `store` that replaces the text of the active script asks a confirmation its `draft` class does not require: `<name> (<id>) is the script currently filtering incoming mail. Replacing its text changes how the next message is handled, as soon as this call lands.`

A `store` uploads the text, has the server compile it, and only then writes the script; a text that does not compile is refused with `Refused: the script does not compile, so nothing was stored. The server's compiler said:` followed by the compiler's message.
Every refusal past the upload adds that the server holds the text unreferenced and that no tool here can remove it.
A successful `store` reports that storing does not activate.

Confirmation: an `activate` reads the source first and names the wide-radius actions it contains, in severity order and with their consequence, `discard`, `redirect`, `reject`, `ereject`, `vacation` and `fileinto`, then names the script that stops filtering, or says that the vacation response switches off when that is what was active.
The detection is lexical and over-detects on purpose: a keyword inside a string or a branch that never runs still counts, because an unannounced `discard` costs mail with no copy anywhere.
A `deactivate` names the script that stops, or the vacation response that stops answering; a `delete` reads `Permanently destroy N scripts: <name> (<id>), … and N more. Sieve scripts have no trash: the source goes with them and no later call brings either back.`
A `store` asks only when its class is set to `confirm` or when it rewrites the active script, with `Store a new Sieve script named <name>.` or `Replace the text of <name> (<id>) and name it <name>.`; the [write policy](../../explanation/write-policy.md) decides whether each class is allowed, confirmed or denied.

An activation or a deactivation reports what it asked and what was active when it read the account, never that the switch landed, since the server answers with no script named; `sieve_scripts` reads back what is active.

Example prompts:

> Store this script under the name newsletters, but do not turn it on yet.

> Make the newsletters script the one that filters my incoming mail.

## Vacation response

Manifest `sieve-vacation`, on the `vacationresponse` capability alone.

### vacation_manage

Reads and changes the vacation response of the account, the automatic reply sent to whoever writes while the account is away.
`show` returns the subject, both bodies, the window, whether the reply is switched on, and whether it is answering today, since a reply left on outside its window answers nobody.
`set` writes only the properties the call names: one left out is kept as it stands, one set to null is cleared, and naming `isEnabled` is the only thing that switches the reply on or off.

Class: `draft` on `show` and on a `set` that does not name `isEnabled`, `send` when a `set` names `isEnabled`, whichever value it carries.

| Argument | Type | Required | Meaning |
| --- | --- | --- | --- |
| `action` | enum: show, set | yes | Read the automatic reply as it stands, or change it; `show` takes nothing else |
| `subject` | string or null | no | On `set`, the subject of the reply, 512 characters at most; null clears it |
| `textBody` | string or null | no | On `set`, the plain-text body, 2048 characters at most; null clears it |
| `htmlBody` | string or null | no | On `set`, the HTML body, 2048 characters at most; null clears it |
| `fromDate` | string or null | no | On `set`, when the reply starts answering, a UTC date such as `2026-09-10T00:00:00Z`; null clears the bound |
| `toDate` | string or null | no | On `set`, when it stops answering, same shape; null clears the bound |
| `isEnabled` | boolean | no | On `set`, whether the reply answers at all; left out, the current state is kept |

The schema itself refuses a `set` naming no property and a `show` naming any.

**Refuses or asks.**
Under `policy.destroy: deny`, switching the reply on is refused before any question, because it stops whatever script was filtering: `Refused: switching the automatic reply on makes the vacation script the active one, which stops whatever Sieve script was filtering incoming mail — the same effect sieve_write reaches under its deactivate action — and policy.destroy is set to deny in the configuration. Call again without isEnabled to change the wording or the window without touching what filters, or lift policy.destroy first.`
Switching the reply off is not covered by that refusal, since the active script was the vacation one already.
A refusal by the server is reported as `Refused by the server: <reason> Nothing was changed.`
Changing the subject, a body or the window never toggles the reply, so such a `set` asks only if the `draft` class is set to `confirm`.

Confirmation: switching on reads `Switch the automatic reply on: everybody who writes to this account is answered by the server, <window>. The reply goes out under the subject "<subject>". Whatever Sieve script is filtering incoming mail stops being the active one the moment this lands — only one script runs at a time, and the vacation script takes that place.`, with the window and subject merged from the call and the stored values; switching off reads `Switch the automatic reply off: nobody writing to this account is answered automatically any more, from the moment this lands.`, and adds the other properties the same call changes.
The script that stops filtering is never named, because reading its name would take a `SieveScript/get` this manifest is not gated on.
A `set` that names no `isEnabled` reads `Change <properties> of the automatic reply. Whether it answers at all is not touched by this call.`; the [write policy](../../explanation/write-policy.md) decides whether each class is allowed, confirmed or denied.

After a `set`, the answer states the active state either way, and a switch on also says which window applies and that no other Sieve script filters any more.

Example prompts:

> Show me my automatic reply and tell me whether people writing to me today get it.

> Turn on my out-of-office reply from the 10th to the 20th of September with the subject "Away until the 21st".
